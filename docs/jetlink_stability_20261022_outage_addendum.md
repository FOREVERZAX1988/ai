# 附：12:24:00–12:24:45 断链 45 s + 恢复后变钝（2026-10-22 追加）

两个 60 s 稳定性窗口（12:17:13、12:19:02）都判 PASS，但**窗口之后**（12:24:00）掉了一次
链，自动恢复。本附录是那次事件的证据链和恢复后的复测，避免报表的 "PASS" 被误读成"这一小时一直好"。

## 1. 事件时间线（全部来自 swaglog / jetlink-owner.log）

| 时刻 | 事件 |
| --- | --- |
| 12:20–12:24 | trips 聚合里 `held`（回复迟到、沿用上一帧输出）单调爬升：111 → 129 → 132 → 136 → 154 → 181 → 203 → 220，每 30 s 增量 18/3/4/18/27/22/17，比窗口期的 ~4-22 更密 |
| 12:23:55± | 帧回复停止（下面 5 s 判定倒推） |
| 12:24:00 | `large model no answer for 5 s, the small model drives from the next` → 降级小模型；`jetlink fell behind, port sees no host (cc 0)`；`leaving (behind) trips frames 10752 … held 328`（held 占比 3.05%） |
| 12:24:00 | jetlink-owner.log：`the Jetlink app stopped answering on 192.168.10.65` |
| 12:24:05–12:24:41 | 8 次 `not joined yet (nothing answered at 192.168.10.251)`，每次 retry 2 s —— **网关 ICMP 都不通**，不是"只有 App 不应答" |
| 12:24:45 | `dialed 192.168.10.65 over Wi-Fi` → `link ready` → `large model joined mid-drive`，恢复 |
| 12:24:47 | jetlink-owner.log：`the Jetlink app answered on 192.168.10.65` |

判定依据：连 192.168.10.251（默认网关，`ip route` 里那台）都不应答，说明断的是**设备到 AP 这一段**，
不只是手机侧 App。设备侧 NetworkManager 在 12:24 前后没有任何重连/新租约日志（最后一次 dhcp4 事件是
11:59:43 续租到同一地址 192.168.10.79），恢复后地址也没变 —— 所以更像 AP/空口短时抽风后自动重连，
而不是设备重启或 DHCP 换址。

## 3. 把"空口"和"手机侧"分开的一枪

同一时刻两个 ping（各 10 发，间隔 0.2 s）：

| 目标 | 结果 |
| --- | --- |
| 网关 192.168.10.251 | min/avg/max = 1.43 / **2.34** / 4.18 ms，mdev 0.87，0% 丢 |
| 手机 192.168.10.65 | min/avg/max = 21.99 / **28.35** / 41.79 ms，mdev 5.32，0% 丢 |

网关 2.3 ms 说明 AP 与空口本身是好的；到手机多出来的 ~26 ms 全在手机那一跳（Wi-Fi 省电/降频/App 在后台被限）。
wlan0 当前是 5.2 GHz、325 Mb/s PHY（AP A4:F3:3B:29:47:E7），不是弱信号问题。

## 4. 结论与下一步

- 设备侧健康：CPU 39-45%、最高温 66 °C 未降频、20 fps 节拍零停顿、零重传。
- 12:24 那次 45 s 断链是**设备↔AP 段**的短时失联，自动恢复；恢复后 TCP RTT 从 13.6 ms 涨到 40 ms、
  迟回复帧从 1.85% 涨到 3.4%，而**帧节拍和上传耗时完全没退化** —— 瓶颈落在手机侧应答与空口时延，不是本机。
- 建议（C 对照实验）：App 保持前台 + 关掉手机省电/后台限制，再抓一个 60 s 窗口；预期 RTT 回到 ~14 ms、
  held 回到 ~1.5%。若保持后台仍 40 ms，则基本可锁定"手机侧省电/降频"，与空口无关。
