# Macan 纯OP点火报错 —— 雷达握手信号逻辑结论 (0916)

> 分支：macan-long-0915/0916 ｜ 数据源：route 0075(纯OP/坏) vs 0078(融合/好) seg0 rlog 逐帧解码
> 方法：直接解析 rlog 原始 CAN 帧（capnp Event.read_multiple_bytes），逐信号比对 bus2(雷达)/bus128(OP代发)，
>      用 vw_mlb.dbc 信号位定义解码 ACC_02/04/05 及 0x127/0x395。

## 一、核心结论（一句话）
**不存在"单一握手信号"需要 OP 模拟。** 纯OP下雷达在约 9.25s 报故障（charisma 1→2、ACC05 st 2→7），
根因是 relay 物理隔离后，雷达在 CAN2（bus2）上**失去与车辆 ACC 网络的往返应答**，触发雷达自身通信看门狗故障；
不是缺某个握手帧，也不是 panda 拦截。`0x127`/`0x395` 均非握手信号（好路由与坏路由字节级一致）。

## 二、逐信号实测（route 0075 纯OP/坏 vs 0078 融合/好，seg0）

### 1. ACC_04 / ACC_Charisma_Status（start59|2，0=Init 1=verfuegbar可用 [2=故障/未定义]）
| 路由 | 雷达(bus2) charisma 时间线 | 雷达 charisma 直方图 | 说明 |
|------|---------------------------|---------------------|------|
| **0075 纯OP(坏)** | 0→1 @ **3.044s**；**1→2 @ 9.251s** | {0:74, 1:155, **2:1302**} | 故障值与健康值并存，故障为主 |
| **0078 融合(好)** | 0→1 @ **2.679s**；保持 1 不变 | {0:67, **1:1465**} | 全程健康 st=1 |
- **关键**：0→1 的"可用握手"在**两种模式都发生**（~3s 自检完成），不是区分好坏的信号。
- 区分点在于 **1→2 故障跳变**：纯OP在 9.251s 触发，融合从不触发。

### 2. ACC_05 / Status_ACC（start57|3，2=待命 7=故障【本 fork 语义】）
| 路由 | 雷达(bus2) | 直方图 |
|------|-----------|--------|
| 0075 纯OP(坏) | st 2→7 @ **9.251s** | {2:458, **7:2604**} |
| 0078 融合(好) | st 恒 2 | （仅 31.0s 一次 2→0→2，为拨杆开关瞬态，非故障） |

### 3. ACC_02 / Status_Anzeige（start61|3）
- 0075 纯OP：雷达 st 2→7 @ 9.251s；OP代发(bus128)在 9.29s 起 7↔2 每 ~60ms 剧烈翻转
- 0078 融合：OP代发 st 恒 2（{2:883, 0:10}），从不出现 7

### 4. OP 是否代发 ACC 帧？（回应用户"op没代发"疑问）
- 0075 pure OP 中，OP **确实**代发 ACC02(0x30c)/ACC04(0x324)/ACC05(0x10d) 到 bus128(CAN0)：
  bus128 计数 780→1730、804→1730、269→2595。
- **panda 只在点火最初丢弃 2~3 帧**（bus192 计数 780:2、804:2、269:3），之后全程放行 → **panda 不是元凶**。
- 所以用户观察"ACC02/04/05 只有一小段 bus0、之后才见 bus128"是点火启动瞬时，随后 OP 持续代发成功。

## 三、根因判定（基于时序与总线拓扑）
- 纯OP 物理隔离（check_relay=true / relay 断开）：雷达 ACC 帧不再回环到 CAN2。
- 雷达在 CAN2 上**发送其命令后收不到车辆/网关应有的应答帧**（在融合/原厂状态下，relay 会把雷达自身 + OP/网关帧
  回环到 CAN2，雷达看到"总线有人应答"而保持待命）。
- 纯OP 下 CAN2 变成空 stub（radar 只发不收应答）→ 雷达在 ~9.25s（点火后约 6s）判定通信失联 → 自报故障
  （charisma 1→2、ACC05 st→7）。
- 该故障被 OP 捕获后，OP 代发的 ACC02/04 从 9.29s 起在 2↔7 / 1↔2 间翻转（OP 反映 accFaulted 状态），仪表报
  ACC/PAS 故障需服务 —— 与用户 0075 观测完全吻合。

## 四、对"雷达静默/停用"方案的启示
- **不要去补"握手帧"**（无单一握手帧；且 radar 已先完成 0→1 握手，故障是持续失联导致）。
- 根治方向（三条路，供选择，未实施）：
  1. **让 CAN2 总线不体现"孤立"**：纯OP 时在 CAN2 上由 OP 周期性回环/应答 radar 的关键帧（模拟车辆应答），
     让 radar 误以为仍在线 → 保持待命不报故障。需确认哪些帧 radar 视为"必须应答"（候选：0x30c/0x324/0x10d 属 OP 已
     代发，雷达侧看的是别的车辆→雷达回应帧）。
  2. **给 radar 发主动停用指令（UDS/诊断）**：真正关闭 radar 握手/工作（需诊断会话 + UDS 服务，复杂且可能不持久）。
  3. **接受 radar 报故障但用 OP 完全接管显示**（现状矛盾点：radar 故障被 OP 读为 accFaulted 并反映到 bus128）：
     需让 OP 在 pure OP 下**不把 radar 的故障状态当成自己的 accFaulted**，强制显示待命，从而仪表不报错；
     但执行层面 radar 会 st=7，是否仍影响车辆/ESC 需台架验证。

## 五、一句话回应用户各疑问
1. "有没有握手信号" → 有握手（charisma 0→1），但好/坏路由都有，**不是故障根因**。
2. "op没代发acc到bus0" → OP **有**代发，panda 未拦截（仅首帧丢 2~3 帧）。
3. "雷达静默需要UDS？" → 彻底关闭需 UDS/诊断；但更可能的低成本法是在 CAN2 上模拟应答保持 radar 待命。
4. "op自己算的值为什么发故障值" → OP 代发的故障值是**如实反映 radar(Faulted) 状态**，不是 OP 自算错误。
