## 二、问题 1&2：为什么"停了还又起步"、起步是谁发的？

**答案：是 OP 发的 —— `SnGCarController`（`opendbc/sunnypilot/car/volkswagen/stop_and_go.py`）
在 OP 侧 bus2 上代发了一个"人按 RESUME"的按键帧；力矩是原厂 ACC 给的。**

证据（`_probe_resume_pulses.py`，`LS_01=0x10B(267)`，`LS_Tip_Wiederaufnahme 19|1@1+`）：

```
673.55 src=130 (bus2) tip=1  <<< RESUME 按下      ← 第1次
673.58 src=130 (bus2) tip=0  抬起
673.59 src=130 (bus2) tip=1  <<< RESUME 按下
673.68 src=130 (bus2) tip=0  抬起
679.35/679.38/679.39/679.48  同上               ← 第2次
682.47/682.48/682.49/682.58  同上               ← 第3次
```

- `src=130` = bus2 的收条 → OP 确实在 **bus2（CAN.ext，雷达侧）** 写按键，与模块设计一致。
- 因果链在 673.55 上非常干净：**RESUME(673.55) → 原厂 ACC_05 mom 0→63(673.57) → 车动(674.42)**。
  即"起步指令"来自 OP，原厂 ACC 只是被 RESUME 解锁后照做（`CS.acc05_stock_status==3` 闸门已过）。
- 触发条件：`update_stop_and_go()` 用 **planner 原始 aTarget > `_RESUME_ACCEL_THRESHOLD`(0.15)
  连续 5 帧** 就发脉冲（`stop_and_go.py:21/181`）。实车在该驻车保持期
  `carControl.actuators.accel = +0.15~0.18`，**正好骑在 0.15 阈值上** → 三次跨阈 → 三次脉冲。
- 当前 `Params`：`MacanStartStop=true`、**`MacanStartStopDistance=0`（=Off，"纯意图起步，无距离条件"）**
  → 连"距离条件"这层过滤都没有（`stop_and_go.py:160`）。

### 为什么会"误判成前车起步"（前车其实没动）

- 该段控制链里的 lead 是 **视觉 lead**（`radarState.leadOne.radar=0, modelProb=1.00`），
  但 **dRel 被钉死在 10.1 m**，672.5→683.5 共 11 秒一帧不变（其间车速 0↔0.9 m/s，车实际移动过）。
- 原因在 `radard._macan_fuse_leads` A2：原厂 idx 有效 → 用原厂反算距离替换/混合视觉 dRel：

  ```
  _macan_idx_to_drel(idx, v) = t(idx) * (v if v > 5 else 5.0)      # radard.py:341-344
  t(idx) = 0.008969*idx + 0.332                                     # radard.py:37-38
  idx=188 → t=2.018s → d = 2.018 * 5 = 10.09 m   ← 与日志 10.1 m 完全一致
  ```

  **静止时用等效 5 m/s（18 km/h）折算时距**，所以"距离"其实是"时距 × 18 km/h"，
  不是真实距离 → 前车贴得很近也会显示 ~10 m。
- 于是 OP 的跟车/规划在驻车保持期看到"前车 10 m 且 vRel≈0"→ 输出小幅正加速度（0.15~0.18）想收拢车距
  → 撞上 SnG 的 0.15 阈值 → 代发 RESUME → 原厂起步 → 车一动模型 vRel 立刻转负 → OP 又刹停 → 循环。
  **这是一个自维持的极限环，不是"前车真的起步了"。**
  （最后一步"为什么 planner 会持续给 +0.15"只做到"dRel 被原厂抬高 + vRel≈0"这一层，
   要 100% 钉死需再抓 planner 输入快照，见 §6 待办）

## 三、问题 3：为什么最后 st=6、而且 bus2 上也报 6

- **st=6 是原厂 ACC 自己报的，不是 OP 发的。** 解码校验：`ACC_Status_ACC : 57|3@1+`（小端），
  正确解码 `(byte7>>1)&7`，已用 `openpilot CANParser("vw_mlb", bus=2)` 对齐（3c25...53c6 → 3）。
  st=6 帧原始字节 `75070000a405538c` → st=6、`vz=0`、`mom=0`、`ACC_Anhalten=0`、**`ACC_KD_Fehler=1`**
  → 典型的"故障/中止"帧；同时把 `ACC_Wunschgeschw_02` 写成 **1022（失效）**。
- OP 侧行为符合既有设计：`acc_control_value()` 里 `stock_st==6 → 立即发 2 跟随`
  （避免"原厂已故障而 OP 仍报激活"的矛盾窗口，2026-09-01 回放结论）→ 所以 **bus128 上是 st=2，bus2 上是 st=6**。
- 用户问"bus2 报 st=6 是不是原厂 ACC 禁止起步" → **是**：st=6 之后原厂立即回 st=2（待机，683.74），
  设定速度失效、`cruiseState.enabled=0` → 原厂既不给力矩也不保持 → 这才是 683.72 之后
  "brk=0 却自己往前溜"的原因（纯怠速蠕动），最后由驾驶员踩刹车收场。
- **为什么原厂会在第 3 次 RESUME 后中止**：只能到"嫌疑"级别。最像的机制正是本模块自己写的注释
  （`stop_and_go.py:28-31`）：**"原厂 ACC 上升沿检测把每个 0→1 都当一次 RESUME →
  起步状态机反复触发（SnG st6 嫌疑根因）"**。而实测**每条脉冲确实产生 2 个上升沿**：

  ```
  673.548 t1 .558 t1 .568 t1 .577 t1 .577 t0 .587 t1 .598 t1 .608 t1 .617 t1 .668 t0
            └──────── 一次 80ms 脉冲窗口内，中间夹了 1 帧 tip=0 ────────┘
  → 原厂看到 0→1 两次；三次意图 = 6 个上升沿（三次脉冲都是同一形态）
  ```

  即"方案A 的一次干净脉冲"在 **报文层并不干净**（LS_01 在总线上还有另一个周期性写者/
  相位错开，把一个 tip=0 帧塞进了脉冲中间）。要坐实需看原厂 DTC / Cabana 里 ACC 状态机
  当时的转换（用户下一步可提供）。

## 四、问题 4：bus128(OP代发) 的 ACC_02 目标信号不是 bus2 的超集

先排掉一个**统计陷阱**：两边报文速率不同，所以"帧数多少"不可直接比。

| seg | 原厂 ACC_02 | OP 代发 ACC_02 | 双方都有 | **仅原厂有** | **仅OP有** | 都无 |
|---|---|---|---|---|---|---|
| 9  | 1500 帧 / **25.0 Hz**, idx>0=1431 | 999 帧 / **16.7 Hz**, idx>0=964 | 920 | **33** | 44 | 2 |
| 10 | 1500 帧 / 25.0 Hz, idx>0=1500 | 1000 帧 / 16.7 Hz, idx>0=1000 | 999 | 0 | 0 | 0 |
| 13 | 1500 / 25.0 Hz, 911 | 1000 / 16.7 Hz, 736 | 589 | **18** | **147** | 246 |
| 16 | 1500 / 25.0 Hz, 1190 | 999 / 16.7 Hz, 999 | 793 | 0 | **206** | 0 |
| 8  | 1500 / 25.0 Hz, 717 | 1000 / 16.7 Hz, 554 | 392 | **87** | **162** | 359 |

（`_probe_acc02_superset.py`：OP 每帧去配对 0.25s 内最近的原厂帧，速率无关）

- **"原厂 1500 vs OP 1000" 主要就是 25Hz vs 16.7Hz 的刷新率差**，不是目标数差。
  例：seg10 原厂 1500 帧**全部**有目标，OP 1000 帧也**全部**有目标 → 完全一致，用户看到的
  "bus128 信号比 bus2 少"在这一段纯属速率错觉。
- 但**确实存在真不对称**：`仅原厂有` = 原厂雷达报了目标而 OP 的 leadOne（=控制源）没有
  （seg9 33 帧、seg13 18、seg8 87）→ 这类目标 **2.A 之后仪表也不会显示**（仪表=控制源），
  而且**控制侧也没用它**。根因是 `_macan_fuse_leads` 只**修正已存在**的 lead
  （`if not lead.present: continue`），**不会用原厂 idx 凭空造 lead** → 融合结果天然可能是原厂的子集。
- 结论：用户记忆里的"原厂有数据就必须判为有"是**旧显示层（原厂透传）**的规则；2.A 把它去掉了。
  **"2.A（仪表=控制源）"与"bus128 ⊇ bus2"是互斥的两个诉求**：要想 `仅原厂有` 的目标也进仪表，
  必须先让它进**控制链**（radard 里允许原厂 idx 造 lead），那是控制行为改动，不是显示层改动。
- 反向的 `仅OP有`（seg16 206 帧）说明视觉确实补了原厂没有的目标，融合是"双向"的。

## 六、可选改法（待用户拍板，本次未改）

1. **收掉误触发（最小、最贴根因）**：SnG 触发不能只看 `aTarget>0.15`。候选：
   - 提高阈值 + 拉长确认帧（0.15 太贴实测正加速度区 0.15~0.26）；
   - 增加"前车确实在远离"的判据（`leadOne.vRel > +0.3` 或 融合 dRel 连续增大），而不是只看自身加速度；
   - `MacanStartStopDistance=0`（无距离条件）在"贴车 10m 假距离"场景没有保护作用，**设 3~10m 也挡不住**
     （假距离 10.1m 会通过任何 ≤10m 的阈值）→ 关键还是判据本身。
2. **修 `_macan_idx_to_drel` 的静止语义**：`max(v,5)` 在 v<1 m/s 时把时距放大成 18 km/h 的"距离"，
   直接抬高了 planner 的目标车距（本事件里 10.1m 假距离是 aTarget 为正的源头之一）。
   候选：低速段（v<1~2 m/s）不融合原厂距离 / 只用视觉 dRel，或对静止目标改用"停车距离"语义。
3. **让每条 SnG 意图只产生 1 个上升沿**：修掉脉冲中间的 tip=0 洞（报文层），并仍保留"一段驻车 =
   最多一次 RESUME"。当前 3s 冷却挡不住本 case（脉冲间隔 5.8s / 3.1s）。
4. **（更大）radard 允许原厂 idx 造 lead** → 才能满足"原厂有必须判为有"；会影响控制（会为原厂-only
   目标刹车），且要处理 `|yRel|` 邻道假目标（2.A 文档 §5 已列残余项）。
